# Vivi Bot 产品与落地规划

> 原型规划存档：后续目标架构以 [Vivi 架构决策：真实会话与持久编排](vivi-conversation-architecture.md) 为准。下文 Run / Task / Attempt 层级及任务详情描述属于原型，尚未按新决策重构。

状态：已获用户确认，首版 A/B 的执行闭环已在 `vivi-bot` worktree 实现并通过本地验证；历史搜索、归档与结果未读计数仍列在后续项。名称为 **Vivi**，复用现有桌面宠物形象。实现与验证说明见 [Vivi Bot 实现说明](vivi-bot-implementation.md)。

依据：[Bot Router / Worker 架构调研](bot-router-architecture-research.md)，并核对当前 Electron 工作树中的 Vivi、Agent Team 和 App Server 实现。本次没有重新验证调研引用的外部产品页面。

## 1. 产品定义

**Vivi 是 FastVibe 中可以持续交办事情、并行处理任务、完成后回来汇报的个人助手。桌面宠物是同一个 Vivi 在桌面上的呈现。**

- 侧边栏固定入口叫「Vivi」，使用现有宠物形象，不增加「Bot → 我的 Bot」两级入口。
- 普通项目会话继续适合深入讨论和直接操作；Vivi 适合连续交办多件事、跨任务跟进和接收结果。
- 第一版只有一个 Vivi。底层保留身份 id，不实现多 Bot 编辑器、市场或 Bot-to-Bot 协作。
- Vivi 页面可用与桌面宠物可见分别控制。现有 `viviEnabled` 继续只表示桌面宠物开关，关掉宠物不停止任务。
- 本地执行依赖宿主进程存活：关窗口与退出应用分别处理；休眠或退出后不能承诺继续工作。远程常驻执行放到后续阶段。

## 2. 主界面与交互

主界面以长期聊天为中心：顶部 Vivi 头像、名字与简短状态，中央对话，底部输入；任务和产物按需打开。

| 位置 | 行为 |
| --- | --- |
| 侧边栏 Vivi | 打开长期主聊天，显示运行/等待处理/未读结果的聚合状态 |
| 顶部状态 | 如「正在处理 2 件事」「有 1 个问题等你回答」，点击展开任务列表 |
| 主聊天 | 用户交办、Vivi 的必要回应、问题、阶段成果和最终结果 |
| 任务卡片 | 名称、真实状态、所属项目、补充要求、停止/继续/重试入口 |
| 任务详情 | 执行过程、Worker 转写、变更、产物、历史尝试 |
| 桌面宠物 | 显示状态与完成通知，点击返回相应工作现场 |

不在首屏展开内部任务图。复用已有消息、问题、文件、Office、Git diff 和资源视图，但页面绑定显式的 Router conversation id，不借用普通会话的全局 activeId。

### 连续输入的语义

一个长期聊天承载多件事，但每件工作有独立任务身份。

- 「整理这周发布记录」：新任务。
- 「再做一份用户说明」：可独立的新任务，必要时依赖发布记录任务。
- 「刚才的发布记录加上中文」：追加到指定任务。
- 点击任务卡片的「补充要求」：输入携带明确 task/run id，不让模型猜归属。
- 纯聊天、询问状态：直接回答，无需每条消息生成一个工作任务。
- 自然语言不足以区分目标时只问这个歧义；显式选择的项目或任务优先于推断。

Vivi 的 Router 每次只短暂处理输入、派发或汇总，之后释放当前回合。Worker 持续执行时，用户仍可提交新任务；Router 自己忙时输入可靠排队，不能把所有新输入当成对旧任务的 steer。

停止具有明确范围：任务卡片停止该任务；一件事的停止取消其尚未结束的子任务；「停止全部」单独提供。普通 Router 回合结束不能取消后台工作，已停止的任务不能被迟到报告重新启动。

### 结果与追问

结果必须指向具体任务与具体产物，并注明完成范围、验证证据、未完成部分。Worker 进程正常结束不等于用户目标完成。代码、办公文档、调研都采用相同任务模型，各自提供适合的验收证据，不以 commit/PR 作为通用完成标准。

主聊天是长期关系，模型上下文并非无限：复用已有压缩，补入当前任务摘要，详细历史按任务读取。尊重现有长期记忆开关，不因启用 Vivi 而自动开启跨会话记忆。

## 3. 复用原来的宠物

已存在的基础：

- `resources/vivi/vivi.glb` 与 `vivi-model.ts` / `vivi-renderer.ts`：模型、材质、配色与渲染。
- `components/fastvibe-mascot.tsx`：现成的应用内 SVG 形象，支持配色、状态、尺寸及关闭动画，设置页已经使用。
- `src/shared/vivi.ts`：六种状态及大小、透明度、位置等偏好。
- `src/main/vivi/pet-window.ts`：独立模型窗口和通知窗口、拖动、抛掷、全屏与位置管理。
- `vivi-completion.ts` / `vivi-notification.ts` / `vivi/agent-bubble.tsx`：成功完成结果选择、迟到读取保护、五秒寿命及悬停/移动暂停。

建议接法：

1. 名称、头像与宠物使用同一身份。侧栏和页面标题直接复用 `FastVibeMascot`，桌面继续用 GLB，避免每行常驻一个 3D renderer。
2. 将 Bot 任务状态投影到现有 `idle/thinking/working/waiting/success/error`。运行标记来自执行事实，不从回复文字猜。
3. 保留单击宠物的互动动画，将双击和右键的打开动作接到 Vivi 主聊天；通知携带自己的导航目标，点击进入产生结果的任务或普通会话。
4. 继续保留普通会话的完成提醒能力。Bot 的中间 Router 回合和各个 Worker 不各弹一次通知，最终交付有唯一 delivery id，避免重复提醒。
5. 保留「仅主窗口在后台时显示成功最终结果」、五秒隐藏、悬停保留、移动时暂停等现有规则。问题和失败在主页面标记，并沿用系统通知渠道。
6. 不恢复宠物旁的第二套完整聊天框。输入、附件和回答问题统一回到主窗口。
7. 保持模型窗口固定为宠物大小，文本由独立通知窗口承载；不要用通知高度扩缩模型窗口。

需要新增的主要是状态/通知/导航适配，不是重做宠物或物理动画。聚合状态与通知目标必须分离：当前正在显示哪项工作的动作，不得改变已经显示的通知点击去向。完成动画结束后重新计算全部活动任务，不能沿用当前“五秒后直接 idle”的路径，把别的未完成任务画成空闲。

现有 `vivi:*` 是本机桌面控制，远程策略拒绝它们。Bot 业务通过新的 `bot:*` 中立调用提供，不能为了手机访问 Vivi 而放开整个宠物控制面。

## 4. 技术结构

```text
Vivi 主聊天                         桌面宠物
    │                                ↑ 状态 / 完成交付
    ▼                                │
BotOrchestrator ──────────────────────┘
    ├── Router：理解、派发、提问、汇总
    ├── Store：Run / Task / Attempt / Input / Report / Effect
    ├── Scheduler：并发、依赖、写入范围冲突、取消
    └── WorkerRunner：复用现有 SDK 与 Agent Team 执行能力
             └── 文件 / 终端 / 浏览器 / MCP / Office

调用与事件：复用中立调用表 + App Protocol + snapshot
存储：已有 fastvibe.db + SDK 转写文件
```

新增领域服务建议放 `src/main/bot/`；现有 `src/main/vivi/` 继续专注桌面呈现。避免将编排继续堆入 `PiProcessManager`。

| 对象 | 定义 |
| --- | --- |
| Profile | 固定默认 Vivi 的身份与默认配置，保留稳定 id |
| RouterConversation | 长期聊天，明确 Bot 归属，复用会话转写和快照 |
| Run | 用户交办的一件事，跟进消息可以属于同一个 Run |
| Task | 为完成该件事拆出的执行单元 |
| Attempt | 某次启动、重试或恢复，绑定 Worker 与执行代次 |
| Input / Report | 用户追加要求与 Worker 结构化结果，含稳定来源 id |
| Effect / Delivery | 已提交但仍需启动、投递、汇总或展示的工作及其回执 |

简单工作通常一个 Run、一个 Task、一个 Worker。复杂工作才拆分，并以依赖确定顺序。首版单层 Worker 即可；不额外开放递归协调者。现有 DAG 的并发、取消和写路径冲突规则可复用或提取；独立任务不为套用 DAG 人为建立依赖，也不另起一组无限制执行名额。

Worker 接收任务相关上下文、项目与验收标准，不默认复制整个长期 Vivi 聊天。第一版显式使用有限任务上下文，避免把所有无关工作泄露或堆积到每个 Worker。

## 5. 现有基础与必须补齐的缺口

### 5.1 主动汇总需要专属唤醒机制

`agent-team-context.ts` 在下一次模型请求时注入结果，明确不唤醒空闲/停止的父会话；`finishTurn` 只提交线程状态与邮箱结果。因此直接套现有 Agent Team 无法保证 Vivi 派活后自己回来汇报。

新增仅属于 Vivi 的 durable Router inbox：用户输入与 Worker report 先落库；单个 Router 串行消费，同一结果只触发一次逻辑汇总。执行重试时以输入/交付 id 对账，而不是承诺模型请求永不重发。用户停止/暂停设置执行代次，失效代次的消息只能保留为历史，不能唤醒它。普通会话保持现有“不自动唤醒”规则。

### 5.2 持久线程不等于持久执行上下文

当前 `SubagentTurnRunner` 使用 `SessionManager.inMemory`，完整展示转写存入进程内 `#subagentMessages`；SQLite 保存的是线程、邮箱和最终结果。`followupAgent` 主要依靠近期邮箱消息重建上下文，并非从原始完整执行点继续。

Vivi 的 Attempt 需要持久会话/可读转写、报告与产物引用，并记录模型、工具与工作目录配置。复用执行器时增加可选的持久会话宿主，不应将改动强加给所有临时子 Agent。

首版恢复承诺是：任务不丢、执行记录可读、状态真实、可显式继续。应用重启把未确认结束的执行标成 interrupted；不自动重放发送消息、发布、删除等可能已经发生的外部动作。恢复先核对工作区和已记录结果，再创建新 Attempt。

### 5.3 幂等需要越过进程重启

App Server 当前幂等缓存是内存 Map，可复用协议形状，但不足以防止重启后重复创建任务。接受请求、写任务、写待启动 effect 在一个事务完成；启动与 report 使用 attempt id 和 generation 对账。数据库写失败时不能真的启动 Worker。

副作用队列提供至少一次尝试和可对账状态，不能据此宣称任意外部操作 exactly-once。外部 API 是否支持幂等回执需要按渠道处理。

### 5.4 问题的恢复不同于窗口重连

现有 pending UI 存在 Main 的内存 Map，快照可以支持窗口重连，但进程退出会失去等待中的 Promise。

任务层持久化问题内容、所属 task/attempt、问题 id、答复及状态。进程重启后显示「需要继续后处理」或重新发起有效问题，不能让旧按钮声称还能回答已经消失的调用。用户等待期间释放 Worker 执行名额，答案通过下一次执行交回。

### 5.5 运行状态与业务状态分别表达

推荐任务状态：排队、处理中、等你回答、已完成、失败、已中断、已取消；停止中的执行可另显示「正在停止」，直到宿主确认退出。执行状态由 runner 报告，业务完成由结构化结果与所需验收决定。

Router 回合结束时，后台 Task 仍可能进行；Vivi 顶部状态和宠物必须读任务聚合。`Run` 完成才交付最终通知，不能直接把任意 `agent_settled` 当成整件事完成。

## 6. 第一版的边界

- 一个全局 Vivi、一个长期 Router conversation；多个本地任务可以并行，每个任务绑定明确项目或独立产出目录。
- 先实现单件事内的本地任务拆分与简单依赖；不同独立任务可使用不同本地项目。复杂跨项目协作与 SSH 执行随后加入。
- 同仓库写任务按声明范围保守串行；未声明时视作整个仓库。范围是协调约定，不声称 cwd 或工具白名单构成文件系统沙箱。
- 不自动创建 worktree；遵守现有显式同意规则，用户选择隔离执行后才创建。
- Router 负责短决策与汇总，Worker 负责执行。模型沿用已有可用模型选择，首版不增加一排强制配置。
- 复用现有工具与用户授权语义，不把旧调研里的通用审批/风险分级系统作为第一版前置条件。需要用户决定时复用问题界面；新增外部入口身份控制属于后续渠道工作。
- 不默认 commit、push 或发布；用户明确交办时按任务要求执行。
- 任务历史进入搜索与费用统计，但复用转写/使用记录的稳定身份，避免 Router 汇总引用 Worker 用量后重复计费。
- Router 主聊天不参加普通空草稿回收和自动归档；历史 Run 可单独归档，不能删掉仍在运行的执行。
- 不因初始化 Vivi 就调用模型或自动打开宠物；未配置模型时沿用现有添加模型入口。

## 7. 交付阶段及验收

| 阶段 | 交付内容 | 必须证明的行为 |
| --- | --- | --- |
| A：第一条闭环 | Vivi 入口、复用头像、长期主聊天、单任务单 Worker、持久记录、结果唤醒 Router、产物入口、宠物最终通知 | 交办任务后离开页面，完成后收到一次汇报，点击通知找到正确任务；重启能解释任务现场 |
| B：可日常使用的首版 | 多任务输入、受限并发、简单依赖、定向追加、独立停止/重试、问题归属与恢复、Worker 详情 | A 未完成时可交办 B；停止 A 不影响 B；迟到消息不复活 A；重启不丢问题与结果 |
| C：持续工作 | 与现有定时任务整合、可复用任务说明、长期记忆读取优化、跨项目与远程执行 | 定时任务与手动任务使用同一套状态/交付，宿主离线时行为明确 |
| D：外部入口 | 先接一个 IM 渠道，独立身份、来源去重、App Protocol 客户端、出站回执 | 重连和重复消息不重复建任务，结果发回正确线程，撤销渠道权限不会影响手机连接 |

建议 A 是内部演示闭环，B 才作为面向用户的首版。A 的持久化和通知不能拖到后续补，因为这是后台助手成立的基础。C、D 不与多 Bot 功能捆绑，只有实际需求出现后再开放多个身份。

首版验收场景：

1. 「整理本项目发布记录并写成文档」产生真实文件，可预览、定位。
2. 第一个任务执行中再交办第二件事，两个任务各自可追问、各自返回结果。
3. Worker 完成时 Router 已空闲，依然能主动汇总；用户停止任务后不能被汇总流程重启。
4. 任务执行中退出并重开，任务标为中断，历史可读；继续前核对已经产生的效果。
5. 问题在后台出现时能定位到具体任务，答案不会误投另一任务或失效的执行。
6. 关闭宠物后任务继续；开启宠物时仅最终交付通知，拖动与落地过程中不跳位、不重复计时。

## 8. 对原调研的具体收敛

沿用：Router/Worker 分工、长期聊天、Task 与 Attempt 分离、提交后副作用、快照、轻入口、结果可追溯。

收敛：名字与形象固定为 Vivi；首版不开放多个 Bot；宠物是表现层；外部 IM、通用审批系统与完整 Source/Eval/Mandate 不作为第一版依赖。

补充：专属 Router 唤醒、Worker 转写落盘、持久问题、跨重启幂等、通知去重与停止代次。这些是当前代码与长期后台助手目标之间的具体差距。
