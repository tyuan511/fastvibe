# Vivi 内置记忆层设计：Markdown 文件方案

状态：已实现并接入 Vivi 宿主。记忆内容使用 Markdown，不新增数据库表或用户配置；验证入口见文末。

## 1. 决策

**沿用 FastVibe 原有的文件式记忆：提炼会话笔记，再整理成 `MEMORY.md` 和 `memory_summary.md`；模型先看摘要索引，需要细节时搜索、读取 Markdown。**

Vivi 使用独立的记忆目录，功能始终开启，没有设置入口、开关、模型或频率选项。不读取普通长期记忆的 `enabled` 配置；关闭或清空普通聊天的长期记忆不影响 Vivi。

不为这层记忆新增数据库表、事实记录模型、SQL 检索、向量库或 embedding 服务。Markdown 是记忆内容的权威来源。少量处理游标、来源指纹和失败重试信息放在内部 JSON 文件中，这些只用于恢复与去重，不保存另一份记忆正文，也不属于用户配置。

保留当前持续 Router + 持续 Worker 的架构。工作状态、队列、问题和结果仍走现有 Bot 存储；不将它们复制进记忆文件。

## 2. 文件结构

建议放在 `runtime/engine/vivi/` 下，与普通聊天的 `runtime/engine/memories/` 分开：

```text
vivi/
  outputs/                        现有工作产物目录
  memories/
    memory_summary.md             简短偏好 + 主题索引，自动注入上下文
    MEMORY.md                     按主题组织的详细偏好、约定、事实、经验
    raw_memories.md                阶段一笔记集合，供整理使用
    rollout_summaries/             按已处理输入范围生成的会话提炼笔记
      <时间>-<来源指纹>-<主题>.md
  memory-state.json               处理进度、来源指纹、空结果、重试、发布版本
  memories-baseline/              最近成功整理后的文件基线，用于生成差异
```

这套目录含义与现有记忆一致。首版不自动生成技能，不扩展其他知识库目录。

### `memory_summary.md`

沿用第一行 `v1`、总长不超过 20,000 个 UTF-16 字符的现有格式。大部分篇幅用于主题索引和明确的读取指引，不能被最近一个长任务挤满。

```markdown
v1

## 用户偏好
- 回复先给结论，解释放在后面。

## 常用约定
- 周报默认使用“已完成、风险、下一步”三段。

## 记忆索引
- 周报写作：结构、口径和输出习惯见 MEMORY.md 的“周报”章节。
- 项目 A：验证方式及已知限制见 MEMORY.md 的“项目 A”章节。
```

摘要是入口，不承载完整执行历史。超出预算时将细节移入正文，保留主题标题和检索路径；复用当前按章节分配预算的做法，不直接截掉后半段。

### `MEMORY.md`

按自然主题组织，不把 Markdown 写成一行一条数据库记录。例如：

```markdown
## 周报

适用范围：用户的个人周报。

- 默认依次使用“已完成、风险、下一步”三段。
- 这是长期约定；某次输入明确指定其他结构时，以本次输入为准。

来源：用户输入 <inputId>，会话 <conversationId>，时间 ...。
更多背景：rollout_summaries/<文件名>.md。
```

项目知识明确写出真实仓库、文件或服务身份；经验写清适用条件、验证时间和已知限制。Vivi 所有 Worker 共用 `outputs` 目录，不能据此认定它们属于同一个业务项目。

### 会话提炼笔记与内部状态

`rollout_summaries/` 保存原始要求、可复用笔记、验证依据和必要来源引用，不复制整份转写、附件或截图。笔记文件名由稳定来源范围和内容指纹确定，重复事件不会生成重复文件。

Vivi Router 可能长期不结束，因此笔记按“这段已处理输入”生成，不反复用整份 Router 历史覆盖一篇摘要。同一用户要求被转给多个 Worker 时，仍引用同一个原始输入，不能将转载算成多次独立验证。

`memory-state.json` 仅保存每个会话已处理到的输入/结果位置、指纹、空结果与失败重试、最近整理版本及擦除代次。丢失状态时可以从已有笔记及来源重新对账；不能把状态文件当作记忆正文。

## 3. 提炼时机

保留原有“阶段一提炼 → 阶段二整理”的方式，针对 Vivi 的持续会话调整触发时机，不沿用等待整个会话静默六小时的条件。

### 3.1 明确的“记住、更正、忘掉”在当前回合处理

用户说“以后周报都这样写”时，Router 使用当前模型的理解结果，向宿主提交对相关 Markdown 段落的有界编辑。宿主检查当前输入身份、epoch、用户原话来源、预期文件版本和修改路径，将正文、摘要与必要的来源笔记一致发布后，才能回答“已记住”。

- 复用 Router 当前回合，不为一个明确约定再开一次同步提炼模型请求。
- “这次简短点”只作为本轮要求，不写成长期偏好。
- 更正时替换原约定，并同步修改摘要；不在另一个角落追加相互冲突的两条规则。
- 一句话同时包含长期约定与具体工作时，先保存约定再分派，同时在本轮工作说明中保留完整要求。工作不能依赖后台整理完成才正确执行。
- 语义不清楚时按正常对话澄清，不为每次记忆维护弹确认框。

这里的写入是宿主控制的记忆维护入口。Router 不因此获得任意 shell 或任意文件写入权限；Worker 仍遵循只读记忆规则。与原有执行工具一样，这不是额外的文件系统沙箱声明。

### 3.2 普通输入处理完、Worker 报告后后台提炼

在当前输入真正结束后登记待处理来源，短暂空闲时合并处理。初始建议约 30 秒合并事件、同一目录单个提炼/整理者；具体参数作为内部代码策略，不提供配置。

阶段一读取新增的用户要求、回答、结果和必要验证片段，沿用原有结构化提炼输出，再生成 Markdown 笔记。来源选择按输入回执与内容指纹完成，不按文件 mtime 把整份活跃会话反复提炼。

以下内容不触发提炼：纯寒暄、快捷进度查询、阶段状态、只有模型回复的片段、已处理的同一内容。模型思考、整段工具日志与整份附件不进入记忆材料。

工作完成可提炼有效方法；失败也可以留下有证据的限制和失败条件。`bot_report` 的成功自述及其 evidence 字符串本身不等于验证，无法支持的推断应明确标为待核实，不写成确定经验。中断不能被整理成“已成功完成”。

阶段二在笔记变化时，以原有文件差异方式整理 `raw_memories.md`、`MEMORY.md` 和 `memory_summary.md`：合并同义内容、纠正旧值、保留来源、更新主题索引。没有变化不调用整理模型。

### 3.3 启动、成本与故障

- Vivi 记忆服务随宿主启动，恢复尚未处理的来源；新安装无需用户启用。
- 首次上线从当前输入起点开始积累，不静默扫描所有旧历史。
- 复用轻量模型选择和可用会话模型回退能力，不读取普通长期记忆的专属模型配置；Vivi 没有独立模型选项。
- 没有可用模型时保留待处理位置，已有 Markdown 仍可读取；模型可用后继续处理。
- 提炼失败有限重试并退避，坏输出不覆盖上一次有效记忆。后台提炼不阻塞发送、分派、工作交付或进度查询，不触发宠物消息。
- 后台整理 agent 使用临时工作副本，仅有记忆目录内的文件整理能力，不加载自身记忆或执行工作工具。沿用原有提示词与校验机制，只调整 Vivi 的来源、常开策略和明确约定优先规则。

## 4. 分派 Worker 时如何使用记忆

采用原来的“摘要先到、正文按需读”，不建设新的语义检索系统。

### 4.1 Router 先获得摘要

每条实际开始处理的 Router 输入，收到 Vivi 的隐藏记忆摘要快照及稳定读取规则。内容未变化时不重复追加；压缩或重载后根据实际会话投影补回。

Router 当前没有普通文件读取工具，因此补充两个小型只读能力：

- 搜索 Vivi 记忆目录内的文字，返回文件、章节和有界片段。
- 按路径与行范围读取该目录内的 Markdown。

这些工具只服务本目录，不给 Router 开通通用 shell 或任意文件浏览。Router 从索引判断应读哪个主题，不需要每次读取全部正文。

### 4.2 分派携带需要阅读的记忆引用

创建或补充 Worker 时，Router 传递目标、材料、完成标准，并可附上自己已查到的相关记忆引用，例如：

```text
工作要求：整理本周周报。
相关记忆：MEMORY.md 的“周报”章节。
```

引用只指向实际存在、已读取的文件/章节。宿主验证它属于 Vivi 记忆目录；选择引用可放在现有分派输入的元数据中，记忆内容仍只保存在 Markdown。

Worker **真正获得执行资格时**，宿主重新读取最新摘要与这些引用，注入有界的相关片段；不把分派时的旧文本永久拼死。引用对应内容已经更正或移动时重新定位，不能拿旧行号冒充当前规则。旧段落找不到时保留摘要索引，由 Worker 按需查阅。

初始建议额外相关片段不超过三段、约 2K token，并受当前模型剩余窗口约束；保留完整的适用范围和来源，不截成半条规则。摘要沿用现有 20,000 字符上限，并同样受实际上下文预算约束。

### 4.3 Worker 按需补读

Worker 与原有记忆读取方式一致：先看摘要，任务涉及某个主题时，用普通只读文件/搜索工具查 `MEMORY.md`，必要时补读对应会话笔记。通常控制在四到六次有针对性的查找，不加载全库。

通过右侧直接补充、回答问题、暂停后继续等不经过 Router 新分派的输入，也会在开始执行时得到最新摘要。没有相关引用时由 Worker 根据任务自己查索引，不能依赖创建会话那一次注入。

新的读取规则明确：Vivi 的记忆文件是历史经验与约定，本轮用户要求和适用的项目规则优先；普通 Worker 不直接修改它们。工作中的新经验由后台流水线整理。

## 5. 写入一致性与历史更新

文件式实现仍需保留基本的一致性，但不引入数据库事实状态机：

- 同一记忆目录的更新串行；安装版与开发版共用数据目录时，使用目录级锁并核对持有者身份，不能只靠某个进程自己的内存队列。
- 后台整理在临时副本中进行。发布前校验 `MEMORY.md`、摘要第一行与预算、路径及符号链接，并确认源文件版本和擦除代次没有改变。前台刚更新了偏好时，旧后台结果必须重做，不能覆盖它。
- 文件通过临时文件和 rename 写入；摘要、正文、来源笔记涉及多文件更新时，使用简短提交记录做崩溃对账。读取也经过同一发布边界，不把“单文件原子替换”说成“整个目录原子替换”。启动先完成或回退未完成发布，再注入记忆。
- 只有记忆文件成功发布后，才推进处理游标和整理基线。崩溃在两者之间时用来源指纹对账，避免重复提炼或丢笔记。
- 原有 `runtimeContextExtension` 的投影去重逻辑可以复用，但 `before_agent_start` 不覆盖所有提供方请求。压缩后若当前投影丢失摘要，需在下一次请求的 context 阶段补入已准备的有效快照。
- 更正或遗忘后，后续请求移除本层旧摘要及失效的派生读取片段；工具调用/结果配对仍保持完整。已经发出的请求和普通历史文字不能靠更新文件撤回。

“忘掉某件事”要清理正文、摘要、相关提炼笔记及会重新导入它的基线/临时副本，取消旧整理结果，并更新来源处理截止点，防止下一轮再次从旧材料提炼回来。不会自动删除原始聊天。已保存的长期偏好不因一个月没使用而被清理；易变技术经验注明验证时间，使用时核实。

## 6. 一个完整例子

用户说：**“以后周报都按完成、风险、下一步三段来，帮我整理本周周报。”**

1. Router 在 `MEMORY.md` 的“周报”章节写入这条明确约定，更新摘要，并保留来源。
2. 写入成功后安排本周工作，附上“周报”章节引用；本轮任务正文也保留格式要求。
3. Worker 开始时读取最新摘要及该章节，按要求产出；不加载无关项目的长篇历史。
4. 工作结束后后台提炼有用的新经验；没有值得新增的内容就只记录处理位置，不重复写入同一约定。
5. 下周的新 Worker 从同一摘要索引找到该约定。应用重启或 Router 历史压缩不影响它。
6. 用户后来要求“以后风险放最后”，原章节和摘要同步改为新约定。尚未开始的 Worker 读取更新后的文件；已完成的周报保持原样。

## 7. 实施范围与复用

尽量复用既有模块：

- `memory-transcript.ts`：提炼材料的可见内容筛选与裁剪，Vivi 补充输入/结果来源锚点。
- `memory-templates.ts`、`resources/memories/`：阶段一、阶段二与读取提示的通用部分；以明确的 Vivi 适配层传入目录、来源和策略，不在原文里掺入产品开关逻辑。
- `memory-workspace.ts`：工作副本、文件差异、基线和产物校验。
- `memory-summary.ts`：摘要预算和完整主题索引保护。
- `runtime-context.ts`：隐藏快照去重与失效投影；补足本次需要的输入/取消校验和压缩后请求级补回。
- 新增轻量 `ViviMemoryService`：独立目录、文件账本、事件合并、受控编辑与发布，随 Bot 宿主启动和退出。

不复用现有全局 `MemoryManager` 实例及其开关，也不把 Vivi 会话重新塞进普通全局提炼队列。Vivi 普通能力不依赖共享摘要；现有普通记忆若仍额外提供，其开关和清理仅影响它自己，不能清理 Vivi 文件。

不修改 `db-schema.ts`，不增加记忆表、设置项、管理页面或宠物通知，不扩展手机/SSH 的记忆宿主。Bot 本身已有的数据库和会话机制照旧。

## 8. 验收

1. 全局长期记忆关闭或被清空，Vivi 仍能积累、读取自己的 Markdown；没有 Vivi enabled 配置。
2. 明确长期要求写入成功才回复已记住；一次性要求不变成永久偏好。
3. 同一主题更正后，摘要、正文和后续注入一致；旧整理不能覆盖新约定。
4. 新 Worker、直接补充、回答、继续及应用重启都能读取最新文件；无关主题不因同一 cwd 被当成一个项目。
5. 同一输入或报告重复到达不生成重复笔记；不反复提炼整个长期 Router 会话。
6. 来源、验证时间和条件可追溯；附件或网页里的指令不能成为用户偏好，未验证完成不变成成功经验。
7. 摘要超长会整理或按章节压缩，主题索引不被末尾截断；模型可继续按文件路径补读。
8. 多文件发布中断、状态游标未更新、并行写入和遗忘时后台返回均可恢复，不丢有效文件、不复活已遗忘的笔记。
9. 模型超时、记忆文件暂不可读或整理校验失败不阻塞正常工作；保留上次有效版本，后台错误不发聊天/宠物噪音。
10. 使用真实 SDK 和脚本模型检查实际请求中的摘要、相关段落、压缩后补回和失效过滤；本设计尚未运行这些实现测试。

本实现使用受控文件发布、请求身份/epoch 校验和隔离整理副本，已接入 `BotRuntime` 收尾事件、Router 记忆工具及 Worker 上下文。回归入口为 `test/vivi-memory-{files,service,sources,extension,integration,boundary}.test.ts`，其中 SDK 测试使用脚本模型，不调用真实供应商。

当前遗忘采用保守策略：保留正文中未被编辑的其他主题，清空原始提炼笔记、重建基线并推进旧来源截止点，阻止旧内容通过释义重新出现。因此无关主题的原始提炼佐证也可能被清理；其已整理正文仍保留。尚在执行的整理副本在操作真正结束后清理，旧结果不能发布。
